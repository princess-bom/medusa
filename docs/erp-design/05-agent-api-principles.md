# 에이전트 API와 승인 원칙

[추측] 에이전트는 자료를 읽고 변경안을 제안한다. 사람은 제안을 저장할지, 실제로 실행할지 결정한다. API는 프로그램이 요청을 주고받는 접점이다. 이 문서는 앞으로 만들 API의 조건이며, 이미 구현된 기능을 뜻하지 않는다.

## 기록 전 승인

[추측] "기록"에는 제안·근거의 영속 저장도 포함한다. 따라서 승인 전 제안은 화면 메모리에만 둔다. 사람이 접수를 승인하면 지정한 제안과 근거만 저장한다. 실행 승인은 따로 받는다. 접수 승인은 주문·발주·가격표·재고의 변경 허가가 아니다.

[추측] 다음은 제안부터 검증까지의 흐름이다.

```text
에이전트 조회·분석
    ↓
화면 메모리의 제안·근거
    ↓
사람의 접수 승인
    ↓
제안·근거 저장 + 승인 대기 pending
    ↓
사람의 실행 승인 approved
    ↓
현재 권한·내용·버전·중복 검사
    ↓
ERP 확정 기록·실행
    ↓
결과 대조 + 실행 증거 기록
```

[추측] 기존 The_IM의 `ask` 요청도 승인 대기 자료를 저장하므로 접수 승인 전에 호출하지 않는다. 사람의 접수 승인 범위 안에서만 제안을 등록한다. `approved`는 실행 허가이며, 실행 성공을 뜻하지 않는다. 에이전트가 "승인받았다"고 쓴 문장이나 보고서는 허가 증거로 인정하지 않는다.

### 작업 상태

[추측] 원본 `lifecycle.ts`의 이름과 전이를 다음과 같이 그대로 사용한다. 같은 상태의 허용된 정보 수정은 전이와 구분한다.

| 현재 상태 | 뜻 | 허용하는 다음 상태 |
| --- | --- | --- |
| `todo` | [추측] 할 일 | `in_progress`, `cancelled` |
| `in_progress` | [추측] 진행 중 | `review`, `blocked`, `cancelled` |
| `review` | [추측] 사람 검토 | `done`, `in_progress`, `cancelled` |
| `blocked` | [추측] 진행이 막힘 | `in_progress`, `cancelled` |
| `done` | [추측] 완료 | 없음 |
| `cancelled` | [추측] 취소 | 없음 |

[추측] 에이전트는 `done`·`cancelled`로 이동하지 못한다. 종료 상태의 정보도 수정하지 못한다. `review`에서 다른 상태로 이동하지 못한다. `review` 상태 안에서 허용된 정보 수정은 별도 승인 대상으로 취급한다. 사람 승인으로 에이전트에게 금지된 전이를 대신 실행하는 우회도 허용하지 않는다.

### 승인 상태

| 현재 상태 | 결정과 다음 상태 | 재시도 조건 |
| --- | --- | --- |
| `pending` | [추측] 사람이 승인하면 `approved`, 거절하면 `rejected` | 아직 ERP에 적용하지 않는다. |
| `pending` | [추측] 대상·정책이 바뀌면 `superseded` | 새 제안을 만들고 다시 승인받는다. |
| `approved` | [추측] 닫힌 승인 | 같은 사람과 같은 승인 내용일 때만 기존 결정 결과를 돌려준다. |
| `rejected` | [추측] 닫힌 거절 | 같은 사람과 같은 거절 사유일 때만 기존 결정 결과를 돌려준다. |
| `superseded` | [추측] 유효하지 않게 된 제안 | 다시 승인하거나 실행하지 않는다. |

[추측] 재사용할 정책 이름은 `ask`, `auto`이다. `deny`를 The_IM의 기존 정책이라고 새로 설명하지 않는다. ERP 확정 기록·실행에는 `auto`를 허용하지 않는다. 실제 정책이 `auto`이면 ERP 실행을 차단한다. The_IM의 사람이 직접 변경하는 경로도 ERP 실행 승인을 대신하지 못한다.

[추측] 접수 승인 뒤의 외부 연동 후보는 `PATCH /api/work-items/:id`, `GET /api/vaults/:vaultId/work-approvals?status=pending`, `POST /api/vaults/:vaultId/work-approvals/:id/decision`이다. 마지막 결정 요청은 사람만 보낸다. 현재 승인 대상은 작업 정보이므로 임의 ERP 발주 실행까지 승인하는 API로 취급하지 않는다. ERP 제안 ID와 정확한 변경 내용을 묶는 연결 계약은 추가 설계·검증이 필요하다.

[추측] 보고서 결과 이름 `completed`, `failed`, `cancelled`도 작업 상태와 구분한다. 원본의 보고서 활성 모드에서는 `review` 진입에 보고서가 필요하다. `done`에는 `completed`, `cancelled`에는 `failed` 또는 `cancelled` 결과가 필요하다. 원본 보고서 모드가 운영에서 활성인지 확인하기 전에는 이 동작을 지원한다고 약속하지 않는다.

## 결정적 경계와 강한 타입

[추측] 결정적 경계는 같은 승인 내용과 같은 자료 버전이면 같은 허용·거절 결과를 내는 서버 검사이다. AI의 문장 해석으로 실행 허가를 만들지 않는다. 모든 확정 쓰기는 한 실행 경계를 거친다. 에이전트와 일반 화면에서 Medusa·레거시의 쓰기 API로 바로 접근하는 경로를 막는다.

[확인한 사실](https://github.com/medusajs/medusa/blob/develop/packages/core/framework/src/http/utils/validate-body.ts) Medusa는 요청 본문을 스키마로 검사하는 기능을 제공한다. [추측] 스키마는 요청에 허용되는 항목과 값의 규격이다. 인증된 주체와 승인 증거도 서버가 다시 확인한다.

[추측] pstack의 Type System Discipline 원칙을 적용한다. 강한 타입은 서로 다른 업무 값과 상태를 섞지 못하게 하는 규격이다. 아래 타입 이름은 구현할 때의 후보이며 이번에 코드를 작성하지 않는다.

| 구분 | 설계 조건 |
| --- | --- |
| ID | [추측] `CompanyId`, `CustomerId`, `PurchaseOrderId`, `ApprovalRequestId`, `ExecutionId`를 구분한다. 다른 거래처의 ID로 바꿔 끼우지 못하게 한다. |
| 수량 | [추측] 수량과 단위를 함께 받는다. 낱개·박스 환산 규칙과 소수 허용 여부를 고정한다. |
| 금액 | [추측] 통화와 금액 정밀도를 함께 받는다. 임의 문자열이나 서로 다른 통화를 합치지 않는다. |
| 제안 | [추측] 대상 ID·기준 버전·변경 전후 값·근거·정책 버전·내용 식별값 `proposalDigest`를 묶는다. |
| 승인 | [추측] `approved`에는 사람 ID·시각·제안 ID·내용 식별값이 반드시 있다. `pending`에는 실행 허가를 넣지 못하게 한다. |
| 실행 | [추측] 작업의 `done`과 실행 성공을 분리한다. 요청 중·성공·실패·결과 불명의 실행 결과를 구분한다. 이 이름을 The_IM 작업 상태에 추가하지 않는다. |

## 승인에서 실행까지

1. [추측] 사람이 저장할 제안과 근거를 확인하고 접수를 승인한다.
2. [추측] 서버가 허용된 제안만 저장한다. 변경 내용·대상 버전·정책 버전의 내용 식별값을 고정한다.
3. [추측] 사람은 변경 전후 값·금액·수량·근거를 보고 실행을 승인하거나 거절한다.
4. [추측] 실행기는 사람의 현재 권한과 승인 상태를 확인한다. 요청 본문의 승인자 이름을 신뢰하지 않는다.
5. [추측] 실행기는 저장된 내용 식별값과 현재 대상·정책 버전을 대조한다. 달라졌으면 실행을 멈추고 새 승인을 받는다.
6. [추측] 실행기는 승인된 명령만 실행한다. 직접 ERP를 쓰는 관리자 화면에도 같은 조건을 적용한다.
7. [추측] 실행기는 실제 결과를 조회하고 증거를 저장한다. 사람은 결과를 검토한 후 작업을 완료한다.

[추측] 권한·버전 검사와 확정 기록 사이에 다른 변경이 끼어들지 못하도록 잠금이나 조건부 갱신을 사용한다. 외부 ERP가 이를 지원하지 않으면 처리 범위를 좁힌다. 안전한 대조가 불가능한 업무는 자동 실행하지 않고 사람이 기존 절차로 처리한다.

## 멱등성 키와 재시도

[추측] 멱등성은 같은 요청을 반복해도 업무 효과가 한 번만 생기게 하는 성질이다. 실행 키에는 회사·업무 종류·제안 버전·실행 대상 시스템을 포함한다. 같은 키와 같은 내용은 기존 결과를 돌려준다. 같은 키와 다른 내용은 거절한다. DB의 고유 조건과 실행 이력으로 동시 요청도 검사한다.

[확인한 사실](https://docs.medusajs.com/learn/fundamentals/workflows/long-running-workflow) workflow 단계 완료 요청은 `workflowId`, `transactionId`, `stepId`, `action`을 가진 키를 사용한다. 로컬 근거는 `www/apps/book/app/learn/fundamentals/workflows/long-running-workflow/page.mdx`이다.

[추측] Medusa 단계 키와 The_IM의 결정 재시도 규칙만으로 외부 발주가 한 번만 생긴다고 보장하지 않는다. ERP 실행 키와 외부 업무 번호를 따로 연결한다. 외부 응답을 잃으면 같은 키로 결과를 조회한다. 조회나 중복 방지를 지원하지 않으면 자동 재실행하지 않는다.

[추측] ERP 기록과 실행 대기 목록은 같은 저장 단위로 남긴다. 이를 처리할 작업자는 같은 실행 키를 사용한다. 외부 성공 뒤 내부 기록에 실패해도 외부 번호를 조회하여 대조한다. 취소·정정은 원 실행을 참조하는 새 제안과 사람 승인을 받는다.

## 에이전트 도구와 증거 로그

| 도구 종류 | 허용 범위 |
| --- | --- |
| 조회 | [추측] 허가된 거래처의 재고·주문·단가 근거만 읽는다. 조회 시각과 원본 버전을 표시한다. |
| 추천 | [추측] 발주량·단가 변경안을 화면 메모리로 제시한다. 누락 근거와 가정을 함께 표시한다. |
| 기록·실행 | [추측] 에이전트에게 도구를 제공하지 않는다. 사람이 승인한 내용을 전용 실행기가 적용한다. |
| 승인 결정 | [추측] 사람 전용 접점만 제공한다. 에이전트 토큰을 사람 세션으로 인정하지 않는다. |

[추측] 접수 승인 후 저장할 증거는 원본 ID·버전·조회 시각, 변경 전후 값, 추천 이유, 미확인 항목, 제안 내용 식별값이다. 실행 승인 이후에는 승인자·시각, 권한 검사 결과, 실행 키, 외부 번호, 결과 대조를 추가한다. 원문 개인정보와 비밀키는 로그에 남기지 않는다. 보관 기간과 접근자는 eddy가 정한다.

[추측] 증거 로그는 덧붙이는 방식으로 남긴다. 실패나 거절을 지우지 않는다. 미확인 항목에는 담당자·해결에 필요한 근거·다음 확인일·실행 차단 여부를 둔다. 필수 자료가 없으면 거절하거나 검토 대기로 돌린다. AI가 빈 값을 채워 넣고 확인 완료로 바꾸지 못하게 한다.

## pstack 역피라미드와 검증

[추측] 구조·타입·테스트를 먼저 적용한다. 규칙 문서는 검사할 조건을 설명한다. 사람 리뷰는 업무 판단을 맡는다. 사람의 실행 승인은 자동 검사 통과 여부와 관계없이 반드시 필요하다.

| 우선순위 | 적용할 장치 | 검증 방법 |
| --- | --- | --- |
| 1. 구조 | [추측] 에이전트에 쓰기 자격증명을 주지 않는다. 모든 확정 쓰기를 한 실행기로 모은다. | [추측] AI 도구와 관리자 직접 API의 우회 요청이 거절되는지 확인한다. |
| 2. 타입 | [추측] ID·단위·통화·승인 상태를 구분한다. 외부 입력을 서버 경계에서 검사한다. | [추측] 회사 ID 혼용, 단위 누락, 승인자 없는 `approved` 입력을 거절하는지 확인한다. |
| 3. 테스트 | [추측] 승인 내용·버전·중복·현재 권한을 실제 저장소와 경계 API에서 검사한다. | [추측] 아래 실패 사례와 정상 실행을 합성 데이터로 검증한다. |
| 4. 규칙 문서 | [추측] 승인표, 상태 전이, 오류 처리와 미확인 항목을 적는다. | [추측] 문서의 규칙마다 실제 차단 지점 또는 미구현 표시가 있는지 대조한다. |
| 5. 사람 리뷰 | [추측] 담당자가 근거·계약·예외와 실행 결과를 확인한다. | [추측] 승인 화면과 실제 기록이 같은 내용인지 대조한다. |

1. [추측] 접수 승인 전에는 제안·본문·근거가 DB·로그에 저장되지 않는지 확인한다.
2. [추측] `pending`, `rejected`, `superseded` 제안으로 쓰기를 요청해 ERP 자료가 그대로인지 확인한다.
3. [추측] 에이전트의 승인 결정, 종료 상태 전환, `review` 이탈을 거절하는지 확인한다.
4. [추측] 원본 전이표의 모든 상태 조합을 비교한다. 사람·에이전트 조건을 각각 검사한다.
5. [추측] 승인 후 내용·수량·정책·권한이 바뀐 요청을 거절하는지 확인한다.
6. [추측] 같은 키의 동시 요청과 승인·거절 경쟁에서 업무 효과와 결정이 한 번만 남는지 확인한다.
7. [추측] 외부 성공 직후 통신을 끊는다. 재조회로 결과를 복구하고 중복 발주가 없는지 확인한다.
8. [추측] The_IM의 `auto`, 연결 끊김, 계약 버전 불일치에서 ERP 쓰기를 차단하는지 확인한다.
9. [추측] 다른 거래처의 단가·주문·근거를 조회하거나 실행하지 못하는지 확인한다.
10. [추측] 정상 승인 한 건을 실행하고 수량·금액·외부 번호·증거 로그를 끝까지 대조한다.

[추측] 위 목록은 앞으로의 구현 검증 계획이다. 이번 문서 작업에서는 실행하지 않았다. pstack의 Prove It Works 원칙에 따라 실제 실행 결과를 보지 않은 항목을 통과로 보고하지 않는다.
